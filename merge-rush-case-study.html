Product problem

Make merge decisions matter beyond matching two identical items.

The early prototype proved that the basic merge interaction worked, but it was too easy to finish while using only a small part of the board. That reduced space-management pressure and made progression feel shallow.

The redesign turns board space, order timing and factory restoration into one connected product loop instead of treating score as the only objective.

Design goal

Readable in seconds, deeper over the full run.

The player should immediately understand drop → merge → order, then discover a second layer: larger footprints, staged board unlocks, repair progression, combos and failure pressure.

Core loop

Short-term orders power long-term restoration.

  1. 01Drop parts from the next queue
  2. 02Merge matching tiers
  3. 03Fulfill the active timed order
  4. 04Earn score, combo and Repair Energy
  5. 05Restore the next factory stage
  6. 06Unlock more board space and higher pressure

Progression system

The factory itself becomes the run's visible progress bar.

01 — Emergency Power

The run starts on a compact usable area so every early placement matters.

02 — Assembly Line

Repair Energy unlocks more cells and expands the decision space.

03 — Generator

Higher-tier order weights increase the need to plan merges ahead.

04 — Robotics Bay

Larger multi-cell items make free space and item orientation part of the puzzle.

05 — Factory Core

The final stage forces a Tier 6 Factory Core order as the Factory Run objective.

Gameplay engineering

Footprint-aware rules make the board a real constraint.

Multi-cell occupancyHigher tiers can occupy 2×1, 1×2 or 2×2 footprints instead of every item behaving like one cell.
Preview before commitDrag/drop placement is validated before the board state is mutated, making invalid moves readable and safer.
Deadlock-aware stateThe rules check legal delivery, merge, placement and movement options against currently usable cells.
Endless damage loopWrong actions can damage free cells; successful deliveries build repair progress that reopens them.

Why it matters

The board is no longer decorative space.

Space becomes a resource. A merge may create the correct item but still be tactically poor if its larger upgraded footprint blocks a future order path. This is the main change that moves the prototype toward a real merge-puzzle product.

Production architecture

Gameplay is separated from platform concerns.

The current development track adds a platform abstraction rather than wiring YouTube-specific behavior directly into gameplay. LocalAdapter and platform lifecycle components keep local development testable while preserving a path to YouTube Playables integration.

Audio management, boot coordination, game-save handling, readiness checks and platform lifecycle logic live outside the core merge rules.

Engineering boundaries

  • GameState — deterministic board & run rules
  • GameScene — Phaser presentation & interaction
  • Footprints — occupancy / placement rules
  • PlatformAdapter — host boundary
  • AudioManager — audio state
  • GameSave — persisted player settings/progress
  • Vitest — regression coverage
