Problema

Un agente que se expresa con soltura puede comportarse igualmente de forma incorrecta.

Los agentes de atención al cliente hacen más que generar texto. Disparan herramientas, avanzan por flujos de negocio, manejan contexto sensible y toman decisiones cuyo orden importa.

Una conversación puede parecer correcta mientras el rastro de herramientas subyacente contiene un envío prematuro, un efecto secundario duplicado, un requisito previo ausente o una derivación insegura. SINAMA trata ese comportamiento como evidencia verificable.

Pregunta de producto

¿Esta versión del agente es lo bastante fiable para un release?

El producto convierte esa pregunta en un pipeline repetible: recogida → ejecución → transcripción y rastro de herramientas → evaluación determinista → regresión y tendencias → release-readiness.

Cómo funciona

Un único pipeline de evidencia desde la selección del objetivo hasta el veredicto de release.

  1. 01Seleccionar un paquete de escenarios o una suite tipada
  2. 02Elegir la demo integrada o un agente HTTPS externo compatible
  3. 03Ejecutar conversaciones multiturno repetibles
  4. 04Capturar la transcripción y el Tool Trace estructurado
  5. 05Evaluar contratos de comportamiento deterministas
  6. 06Comparar versiones, tendencias y release readiness

Motor determinista

La fiabilidad se expresa como contratos explícitos, no como impresiones.

Requisitos de herramientas

Herramientas obligatorias, acciones prohibidas, restricciones de recuento de tools y comprobaciones de argumentos estructurados.

Orden del workflow

Prerrequisitos, orden de llamadas, comprobaciones de existencia y disciplina de side effects.

Contratos de respuesta

Frases obligatorias/prohibidas, reglas regex full-match, rangos numéricos y límites de repetición.

Evidencia legible por máquina

Los fallos, métricas y evidencias están estructurados para poder comparar y revisar ejecuciones.

Regresión y release

Una ejecución de prueba se convierte en una señal de release.

Baseline y regresión

Las ejecuciones pueden marcarse como baseline y compararse entre versiones del agente. El producto distingue comportamiento mejorado, estable y regresivo, incluidos fallos nuevos, resueltos y persistentes.

Preparación para release

Los errores de ejecución y los fallos o regresiones HIGH/CRITICAL pueden bloquear el release. Los problemas MEDIUM/LOW o la falta de contexto baseline pueden generar una advertencia. La evidencia saludable puede producir READY.

Semantic Judge — modo sombra

Semántica consultiva sin anular la verdad determinista.

Línea de desarrollo / integración

El semantic judge es una vía de integración consultiva para rúbricas explícitas como promesas sin respaldo, satisfacción de la intención de la persona usuaria y revelación de instrucciones internas. Se ejecuta después de la puntuación determinista y del enmascarado de datos personales, y no puede modificar el estado determinista, la severidad, las métricas, los fallos, la regresión ni el release-readiness.

Stack de ingeniería

Arquitectura de producto diseñada para la repetibilidad.

Frontend

Dashboard Next.js / React para escenarios, ejecuciones, fallos, regresión y readiness.

Backend

Runner FastAPI / Python, evaluador, adaptadores y capa de persistencia.

Persistencia

Almacenamiento respaldado por PostgreSQL diseñado para rutas de despliegue compatibles con Railway y Supabase.

Seguridad

El enmascarado de PII y las restricciones conscientes de SSRF para agentes externos protegen los límites de evaluación.
