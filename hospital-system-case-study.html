Project Context

Building a database-backed desktop workflow around three user roles.

The project was created as an individual Visual Programming course assignment focused on database-backed registration, login and CRUD operations. Its domain was modeled around a simplified appointment workflow for patients, doctors and secretaries rather than a production hospital environment.

The repository preserves 17 code excerpts, a database schema and interface evidence, but not the original solution, project, Designer, resource or build files. It is presented as a source archive rather than a runnable or deployed product.

User Roles

Three dedicated forms-based workflows

Patient, doctor and secretary journeys are separated through dedicated forms and database credential checks.

Patient

Registration, database credential check, profile editing, branch and doctor selection, available-slot filtering, appointment booking and appointment-list viewing.

Secretary

Database credential check, appointment-slot creation, doctor management, branch management, announcement creation and full appointment-list access.

Doctor

Database credential check, profile information, assigned appointment listing, complaint detail viewing, announcement access and profile editing.

The separation is implemented through dedicated forms and credential checks, not a centralized role-based authorization framework.

Database Design

Six SQL Server tables supporting direct form-to-database operations.

The SQL Server model contains six tables covering patients, doctors, secretaries, branches, appointments and announcements. Forms access these tables directly through ADO.NET commands and adapters, with appointment relationships represented mainly through TC, doctor-name and branch-name values.

Verified boundaries

  • Date and time values are stored as strings.
  • Doctor and branch relationships are stored by text.
  • Patient association uses a TC string.
  • PK/FK/unique/check constraints are not present in the archived schema.
  • RandevuDurum has a default value of 0.

Testing & Limitations

Useful workflow evidence with clear archival and technical limits.

The archived code includes required-field checks and user-facing success or error messages in several forms. Runtime verification is currently blocked because the repository does not include the original solution, project, Designer or resource files, and the implementation also lacks transaction, exception and secure password-handling layers.

Verified in the archive

  • Required-field checks in several forms
  • User-facing success and error messages
  • Database-backed credential checks
  • Parameterized commands in most write operations
  • CRUD and appointment workflow code excerpts

Limitations

  • The repository is a source archive, not a runnable build.
  • Original solution and Designer files are unavailable.
  • Passwords are stored and compared as plain text in the archived implementation.
  • No centralized authorization layer is present.
  • Some SQL filters use string concatenation.
  • Connection lifecycle management is incomplete.
  • Exception handling and transactions are not implemented.
  • Appointment cancellation and rescheduling are not implemented.
  • Database constraints and relationships are limited.
  • Runtime behavior cannot currently be reverified from this repository.

The project demonstrates role-specific desktop workflows and database-backed credential checks, while password security, authorization and privacy controls remain outside the completed scope.
